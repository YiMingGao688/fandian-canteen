# 饭点与苍穹外卖功能核查

核查日期：2026-11-07。对照本地 `upstream-sky` 课程目录、项目保留的原 `com.sky.controller.admin` / `service.impl` 实现，以及饭点实际使用的 `/campus` 接口和 Vue 页面。旧接口存在不代表校园账号和页面可以使用。

当前结论：菜品管理闭环及四项 P1 运营能力已实现并完成本地验证。饭点具备校园预约、分窗口权限和取餐核销能力，P2/P3 中的套餐、报表等仍列为未完成，不能据此宣称全部业务和生产性能已超过苍穹外卖。

## 四项核心运营能力（已完成）

| 能力 | 当前行为 | 代码与验收证据 |
| --- | --- | --- |
| 工作账号管理 | 管理员新增/编辑 ADMIN、STAFF、SCREEN 工作账号，绑定窗口、启停和重置密码；不操作学生；保护当前及最后可用管理员 | `CampusOperationsService`、`CampusOperationsMapper`、`OperationsSettings.vue`、`AdminAccountEditor.vue`；覆盖并发互停管理员、旧会话失效等测试 |
| 窗口与营业设置 | 管理员新增窗口；窗口人员只维护绑定窗口。维护位置、介绍、营业区间、默认容量和营业状态。营业区间真正约束时段发布、下单及改约 | `CampusHours`、`CampusCatalogService.slots/withinHours`、`CampusOperationsService.saveWindow/windowStatus`、`AdminWindowEditor.vue` |
| 全量历史订单 | 服务端总数、分页、状态、取餐日期、关键词和窗口筛选；批量查询一页明细。原最近一百笔接口仅供总览近期队列 | `CampusOrderQueryService.page`、`CampusOperationsMapper`、`OrderDispatch.vue`；临时库验证 137 条历史，实际库核对全量 118 条、原近期 100 条 |
| 拒单和管理取消 | 明细中填写原因后确认；仅待接单可拒单；未支付至待取餐可管理取消；已完成禁止取消。退款失败保留原订单和资源，重复/并发请求只释放一次 | `CampusOrderService.terminate/cancelLocked`、原 `AlipayGatewayService.refund`；并发取消和退款失败回滚测试 |

营业时间最多四段，每段至少二十分钟、不跨午夜，发布当前配置的二十分钟预约网格；调整营业时间不删除历史预约。默认容量用于新发布时段，已有时段保持原容量，避免改变既有预约。暂停营业后，已有订单仍可接单、备餐、核销或按规则取消。

重置密码、调岗或更换绑定窗口会改变令牌的凭据/授权版本，旧会话失效；启停、角色和绑定窗口始终根据数据库校验。此次升级前不含凭据版本的旧会话也需重新登录；未批量修改已有账号密码。

退款沿用现有支付模式：本地演示支付更新演示退款状态，支付宝沙箱订单使用原沙箱退款接口。集成测试模拟支付网关成功或失败，不代表已经完成真实资金渠道验收。

菜名沿用原 `dish.name` 全局唯一规则，目前不同窗口不能建立同名菜品。要改成“同一窗口内唯一”需要另行设计索引迁移，当前未改数据库结构。

有历史订单的菜品保留下架记录，用于取消归还库存和报表追溯。这比直接物理删除更保守，不能将保护规则当成删除按钮故障。

## 已有的校园场景能力

这些属于饭点当前的代码能力，不据此推断外卖课程的全部实现。

- `CampusCatalogService.slots`：今天/明天的预约时段、五分钟截止、名额容量。
- `CampusOrderService.submit/reschedule/cancel`：幂等请求、原子扣库存、按时段预约和改约、取消归还名额。
- `CampusOrderService.pickup`：八位取餐码、按窗口核销、重复核销保护。

- 收藏、已购评价、面向窗口的反馈及回复；`CampusScreenService` 的脱敏运营汇总。

后端脚本只在本项目的本地 MySQL 实例上建立 `fandian_catalog_test_*` 临时库，导入空表结构，运行真实 MyBatis/事务测试后删除该临时库。它比较现有菜单前后指纹，不向业务菜单写入测试记录。JUnit 集成测试默认跳过，仅通过该脚本传入受限临时库配置后运行。

浏览器隔离脚本分别覆盖新增/上传/分类/库存保留、原控件交互、24 组桌面视口与原订单流程；写操作均由独立浏览器上下文拦截。`verify_menu_live.mjs` 另检查实际运行服务的权限、非法请求与真实图片上传/读取，上传验证文件随后定点清理，不提交新增菜品。它们不能替代真实支付、生产权限审计或负载测试。

图片保存在 Git 忽略的 `.local/uploads/dishes`，需要与数据库共同备份。当前没有后台清理取消表单后遗留上传图片的任务；正式部署多实例时还需共享文件存储。现有 OSS 示例接口没有借给校园账号，也没有修改其密钥或生产配置。

## 后续补全：经营报表与批量上下架

已接通日期范围经营报表和 XLSX 导出：入口“运营设置 → 经营报表”，按取餐日期和授权窗口查询，最多 366 天。汇总预约量、已核销量、核销收入、取消量、退款金额，补齐无订单日期；Excel 含每日经营及完整订单明细，收入仅计已核销订单，文本不写作公式，不导出学号、取餐码。导出范围与已查询范围一致，变更条件需重新查询。

菜品列表支持勾选当前页批量上下架，翻页、改变每页数量或筛选时清空选择。每次最多 50 道，先锁定、校验全部归属后一起写入，失败整体回滚；只变更状态，不覆盖旧库存和价格。当前尚无批量删除。

代码：`CampusReportService/Controller`、`BusinessReports.vue`、`CampusMenuService.batchStatus`。新增临时库测试验证 137 条历史、Excel 明细行数、零值日期、越权与库存保留；后端共 50 项通过。浏览器批量选择、翻页清空、报表指标、导出范围保护及三个桌面尺寸检查通过。复跑 `node scripts/verify_reports.mjs`。

当前报表覆盖经营日报和订单明细，用户增长、销售排行等扩展报表仍需补充。剩余项目仍包括完整套餐/结构化口味、实时来单与催单、负载与长期运行验证，未将本次两项完成计作全部差距已补齐。
